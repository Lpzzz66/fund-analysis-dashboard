## 3. `gz` 目录处理结论

`gz` 不是一份应直接全量导入的独立历史数据。最终盘点不按文件名配对，而是先按“产品 + 表内估值日期”聚合，再用 SHA-256 哈希区分重复与冲突：

| 指标 | 最终数量 |
|---|---:|
| 同产品同日期同哈希的重复组 | 1,347 |
| 同产品同日期不同哈希的冲突组 | 6 |
| 主目录独有日期 | 81 |
| `gz` 独有日期 | 0 |

迁移规则：

1. 以三个产品主目录为第一来源。
2. `gz` 中同产品同日期同哈希的文件标记为重复，不再次导入。
3. `gz` 中主目录没有的日期作为候选补充文件。
4. 同产品同日期哈希不同的文件进入“历史冲突”复核，不自动选择。
5. 不移动、不删除、不覆盖源文件；只在系统中记录规范化来源和哈希。

6 个冲突组的产品与表内估值日期为：

- 梦一号：2024-06-24、2026-06-30。
- 千金一号：2025-02-06、2026-07-01。
- 天策上将：2025-01-21、2026-07-16。

旧文档的表格按主目录与 `gz` 的同名文件比较，因此得到的是“同名文件对”的数量和差异。估值文件名通常不带年份，且两个区域存在跨年份放置：同名文件可能对应不同表内日期，不同文件名也可能对应同一表内日期。旧口径适合辅助发现目录问题，但不能作为迁移去重口径。

当前口径以表内“估值日期”为准：同产品、同日期、同哈希计为重复；同产品、同日期、不同哈希计为冲突；某日期只在一个来源区域出现时才计为该区域独有。因此最终结果是主目录独有 81、`gz` 独有 0，与旧文档按同名比较得到的数字不同。

## 4. `.xlsx` 和旁车文件处理

`千金一号估值表\交易记录备份` 和 `天策上将估值表\交易记录备份` 下的 `.xlsx` 是交易记录工作簿的每日备份，不属于当前“估值表唯一数据源”的首期导入范围。

处理方式：

- 首期迁移工具将其识别为“非估值表/暂不导入”，保留源文件。
- 不把交易记录误当作估值表导入。
- 两个 `.bak_cum_nav` 文件也不进入估值导入器。
- 将来如果需要交易归因，可以另立数据源和模块，不复用当前估值表导入模型。

## 5. 历史迁移执行顺序

### 阶段一：建立本地清单

扫描每个文件，生成：路径、扩展名、大小、哈希、候选产品、表内估值日、工作表名、解析状态。

### 阶段二：主目录导入

按产品和估值日顺序导入三个主目录的 1,434 张估值表。首期建议每个产品先导入最近日期向前的少量样本验证，再导入完整历史。

### 阶段三：补充 `gz`

本次没有 `gz` 独有日期，不需要自动补充 `gz` 文件。6 个冲突日期需人工复核后再选择版本；相同哈希只记录重复关系，不重复导入。

### 阶段四：历史质量报告

输出每个产品的日期覆盖、缺口、重复、版本冲突、校验失败、科目未映射和净值序列异常。

## 6. 服务器与本地目录的关系

云服务器不能直接访问本机 `F:` 盘。历史迁移必须通过以下之一完成：

- Windows 客户端的“选择目录导入”功能，扫描后批量上传。
- 一个本地迁移命令行工具，调用同一套上传接口。

迁移工具不得移动、重命名或删除源文件；上传过程失败可以从清单断点续传。
